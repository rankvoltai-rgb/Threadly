# Threadly

Threads lead generator. Search Meta Threads by keyword, get the freshest
buying-intent posts ranked newest-first. The dashboard **is** the landing page —
there is no auth and no signup.

## How it works

1. `POST /api/search` sends your keywords to the Apify `automation-lab/threads-scraper`
   actor in `search` mode, with `postedAfter` set from the selected date window.
2. [`lib/threads.ts`](lib/threads.ts) dedupes by post id, re-enforces the date window,
   scores each post, ranks it, then drops verbatim reposts.
3. Free visitors see the first 10 leads in full; the rest come back redacted.

### Lead scoring

Recency dominates (40 points, decaying over 14 days), then buying-intent phrases
("looking for", "hiring", "budget", "asap"), then a small engagement bonus.
Replies and reposts are penalised. Sorting is **by day bucket first**, so the list
really is newest-first, with score breaking ties inside the same day.

## Data layer

Convex is the source of truth when configured; the app falls back to signed
cookies when it is not, so it runs with or without a deployment. Every route
reports which path it took as `backend: "convex" | "cookie"`.

| Table | Holds |
| --- | --- |
| `licenses` | Purchases, keyed by visitor **and** the Stripe email that makes them recoverable |
| `trials` | Free-lead consumption, server-side so clearing cookies is not a reset |
| `searches` / `cachedLeads` | Cached scrapes, 6h TTL — a repeat search skips Apify entirely |
| `savedLeads` | The pipeline: status (`new`→`contacted`→`replied`→`won`/`dead`) and notes |

Convex is called through typed `makeFunctionReference` handles in
[`lib/convex.ts`](lib/convex.ts) rather than the generated `api` object, so the
app compiles before a deployment exists. All access is server-side via
`ConvexHttpClient` in route handlers, which keeps the visitor id out of reach of
client JS.

### Identity without auth

Still no accounts. A `threadly_visitor` cookie (minted by the first API call)
keys everything. Clearing it loses the visitor id — so **purchase recovery is by
email**: Stripe collects it at checkout, and `/api/restore` re-points the licence
at the new browser. That closes the durability hole the cookie-only version had.

## Setup — Convex

Provisioned on team `orin-ai`, project `threadly`
([dashboard](https://dashboard.convex.dev/t/orin-ai/threadly)).

```bash
npx convex dev       # watch mode: pushes function changes + regenerates types
npx convex dev --once  # one-shot push
npx convex data savedLeads   # inspect a table from the terminal
```

To deploy the backend for a production build, run `npx convex deploy` — the dev
deployment above is separate from prod and they do not share data.

If `convex/_generated/` is ever missing, `convex/*.ts` reports "Cannot find
module './_generated/server'". Run `npx convex dev --once` to restore it; the
Next.js build is unaffected either way, since `tsconfig.json` excludes `convex/`.

## Deploying to Render

[`render.yaml`](render.yaml) is a Blueprint: in the Render dashboard choose
**New > Blueprint** and point it at this repo. It provisions one Node web
service and prompts for the secrets marked `sync: false`.

The build command runs `npx convex deploy` **before** `next build`, so the
Convex functions ship first and the prod deployment URL is injected into the
Next.js build as `NEXT_PUBLIC_CONVEX_URL`. Without that ordering the site would
build against an empty backend.

| Set in Render | Where it comes from |
| --- | --- |
| `APIFY_TOKEN` | Apify console |
| `CONVEX_DEPLOY_KEY` | Convex dashboard → Settings → **Production** deploy key |
| `STRIPE_SECRET_KEY` | dashboard.stripe.com/apikeys |

`LICENSE_SECRET` is generated by Render once and stays stable. `NODE_VERSION` is
pinned to 24; `package.json` requires `>=20.9.0`.

Render sets `PORT` (default 10000) and `next start` honours it — no config
needed. `/api/license` is the health check: it returns 200 without touching
Convex when the caller has no visitor cookie.

**Watch the request duration.** A cold search takes 20–60s and `/api/search`
allows up to 300s. If Render's proxy cuts long requests, cold multi-keyword
searches will fail while cached ones stay fine — the fix is to move the scrape
into a Convex action, which is not subject to the web service's request limit.

### Finishing Stripe

Checkout is fully wired and needs one thing: a secret key from
[dashboard.stripe.com/apikeys](https://dashboard.stripe.com/apikeys) set as
`STRIPE_SECRET_KEY`. It calls the Stripe REST API directly, so no marketplace
integration or SDK is involved — any Stripe account works.

Until the key is set, `/api/checkout` returns a `503` with
`code: "stripe_not_configured"` and the UI surfaces that message rather than
failing silently.

Payment flow: `/api/checkout` creates a $20 one-time Checkout Session →
Stripe redirects to `/api/checkout/confirm`, which **re-fetches the session
server-side** and only mints a license when `payment_status === "paid"`, so a
forged success URL cannot unlock the app.

## Design

Poppins at **600 and 700 only** — those are the two weights loaded, so semibold
is the baseline body weight and bold carries the headings. Anything asking for
400/500 resolves to 600.

Forced black — no light variant and no system switching (`color-scheme: dark`,
`themeColor: #000000`). All text is white or white-alpha; the lead-score pill
encodes rank as **brightness** rather than hue, so nothing depends on colour.

The headline reads "Turn ⊚ IG Thread into …" with the final word cycling every
2.3s through Revenue → New Users → Clients → Bookings → High Intent traffic,
behind an accent highlight bar that wipes in left-to-right.
[`RotatingWord`](components/RotatingWord.tsx) grid-stacks every word invisibly so
the box reserves the width of the longest one — the headline never reflows as the
word changes, and no JS measurement is involved. The rotating word sits on its own
line so the reserved box centres cleanly instead of leaving a gap after a short
word. Screen readers get the list once via `sr-only` rather than a word mutating
every couple of seconds.
The Threads glyph is the wordmark, and [`ThreadsRain`](components/ThreadsRain.tsx)
drifts 34 copies of it behind the hero at 3–11% opacity.

Its positions come from a fixed table, **not** `Math.random()` — random values
would differ between the server and client render and hydrate-mismatch on every
load. `prefers-reduced-motion` keeps the glyphs but stops the fall.

The landing is pinned to a single viewport (`min-h-[calc(100svh-3.5rem)]`, and
the footer only renders once there is content to scroll). Verified at 1440×900,
1280×720 and 390×844 — no scroll at any of them.

## Notes

- The actor is genuinely variable: some phrasings return nothing. Keywords worded
  the way a buyer would write them ("looking for a web designer") return far more
  than category nouns ("design services").
- Searches take roughly 20–60 seconds; `/api/search` allows up to 300s. With the
  Convex cache warm, a repeat of the same (keyword, window) returns in well under
  a second — measured at 37.2s cold vs 0.43s cached.
- `cachedLeads` grows one row per scraped post. Rows past the 6h TTL are ignored
  but not deleted; add a Convex cron to purge them if search volume gets high.
